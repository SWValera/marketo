## Confirmed causal chains

1. `proxy()` and `resolveCurrentAuthContext()` both call `auth.getUser()` in sequence. The built original Worker makes two Auth calls on a valid-session protected page. The same integration test against the revised Worker makes one. Profile and role checks still run, and an Auth outage remains an error, not a signed-out state. `getRequestUser()` shares only a server-verified result inside incoming-request AsyncLocalStorage; it does not authorize from cookie claims or `getSession().user`.
2. The installed PostgREST 2.112.2 retries header `TimeoutError` and 503 responses three times. `fetchWithDeadline()` formerly created another ten-second signal for each attempt. The original timeout test observes four calls. The revised transport normalizes an exhausted header deadline to non-retryable AbortError; server clients explicitly disable SDK automatic retries. Ordinary writes are not replayed by recovery.
3. A failed reference read was not shared between metadata and content. React cache alone did not deduplicate those execution contexts in the installed runtime. With immediate fixture 503 responses, original production code made 16 category requests and took about 15 seconds (two pagination ranges × four SDK attempts × two consumers). The revised Worker makes two requests; a subsequent incoming request fetches again. `requestCache()` retains the failure only for that incoming request. Completed public reference data still has its bounded TTL; no Worker I/O promise is shared across visitors.
4. `requestCategoryAttributes()` retained a pending browser request without any deadline. The test executes that actual function with a stopped response body: original stays stuck and shares that promise on another call; revised aborts, removes it, and succeeds on retry. Consumer cleanup still only detaches its own state updates, not another consumer's transport.
5. vinext 0.0.50's actual `consumePrefetchResponse()` returned null for pending prefetch, so the navigation caller started another request. The same test imports the original and transformed installed module: original fails, transformed consumer waits for the existing public prefetch. Prefetch has its own bounded transport lifetime; the navigation has an independent absolute end-to-end deadline.
6. The old recovery timer restarted on repeated clicks and was stopped by a URL change. Its replacement coordinates the actual RSC navigation entry point, shares same-target work, aborts superseded reads, checks elapsed wall time after visibility/pageshow/online, and waits for router commit, full RSC body and visible non-busy content. It does not automatically reload the document after a read failure. Actual browser behavior remains subject to the browser blocker above; controller and installed-module tests are not represented as a phone test.
7. `findListingBySlug()` was also cached only through React cache. The actual original compiled listing page reads the listing and seller twice for metadata/content (ten data calls); the same fixture test after request-scoped memoization reads each once (five calls). This is a confirmed successful-path cost, independently of timeout recovery.
8. The original Service Worker allowed fifteen seconds for document headers and removed its deadline as soon as headers arrived. A stopped body could then remain pending. Tests execute the real SW in a VM: revised page reads retain the same nine-second deadline through the body and bounded offline fallback. Static/media policy is not shortened; no HTML/private API caching or whole-cache purge was introduced.
9. `app/error.tsx` called only the React error boundary's `reset()`. An actual-component test observes zero new data requests before the fix. Retry now obtains a fresh RSC payload while retaining current query parameters, then resets the boundary. Error payloads cannot enter the visited-response cache.
10. When dynamic filter definitions failed, category/search pages could proceed without the requested filters. The original built page fails the error-marker regression. Revised pages show a retryable failure and do not run an unfiltered listing query; API failure is no longer represented as a successful broad result.
11. `CategoryDirectory` loaded its full tree only on mount. A failed reference request left root categories without a retry control (and without a visible failure when search was inactive). The real-component/real-cache VM regression fails on that source and passes after adding explicit failure/retry without remounting or losing the query. The account-deletion page's read-only Auth failure also now offers retry instead of only a login link; no deletion operation was executed or changed.
12. The browser favorite store retained an unbounded pending dependency/Auth/list read, and a successful set of favorite IDs was reused without an account-change invalidation. Real-store VM regressions fail on the original source. The store now has one nine-second read budget with wall-clock resume checks, passes cancellation to the supported list transport, ignores late unabortable Auth results, and clears private IDs on account changes. A fresh server-verified user is required before loading IDs; identity mismatch prevents a write against stale state. Auth notifications only invalidate, and never authorize or await another Auth operation. No write is automatically replayed. These defects affect widget recovery and account isolation, not the measured server-render latency.

13. Final route review found the same duplicate identity read on login, confirmation-result and password-form pages. `auth-read-before.log` fails on two calls for login; the revised compiled-route regression requires one call for all three pages. Temporary Auth errors now show a localized read retry instead of an anonymous form or invalid-link redirect. Only the actual `/auth/callback` exchange remains outside the page-read deadline, not every `/auth/` GET. The result-page stall regression includes the proxy and response body. Confirmation/password writes were not changed or replayed.

Causes 2–6 and 8–12 amplify failures, prevent recovery or misrepresent results; they do not prove that every initially slow successful request was caused by the API. The additional Auth round trip and duplicate detail hydration are demonstrated successful-path costs. Live unauthenticated HTTP measurements observed zero failures in 100 requests, but a first Home response of approximately 3.35 seconds; the exact network/Worker/database/phone split is not established by that measurement.

`AppLink`/`CategoryLink` prefetch is opt-in/off, while listing-card hover deliberately prefetches after 150 ms. The pending-prefetch defect is reproduced in the installed library, not proved to be the primary source of the reported phone delays. The adapter also prevents private prefetch before network I/O, rejects expired pending entries before awaiting them, and prevents a late obsolete prefetch failure from evicting its replacement. Auth state-change callbacks reviewed here contain no awaited Supabase call: an auth callback deadlock was not confirmed. The automatic city `router.replace()` on direct search/catalog entry with a stored city and no URL city still exists; category links already include city on the first request. ## Invariants for new pages and loaders

- Incoming page/API reads have a shared nine-second server limit, including response consumption. Data requests stop slightly earlier to allow rendering an honest fallback inside that limit. Writes, auth callbacks and media transfers are not subjected to this page policy.
- The browser navigation deadline is ten seconds total, not ten seconds per attempt. Duplicate target clicks share a promise; changing the target aborts the old operation and the router's navigation ID prevents a late commit.
- URL changes, headers and HTTP 200 do not establish useful readiness. Never count an error screen or fallback as successful content.
- Keep independent reads parallel when access permits; do not read protected data before identity/rights checks. RLS and account-status checks remain authoritative.
- Cache public completed values only across server requests. Keep identity, pending loads and failed reads request-scoped. Do not persist protected RSC responses in the cross-navigation cache.
- Retry bypasses a saved page response and retains the current query/city/filter parameters. It never replays writes. Do not add a full-page reload loop, global cache purge per click, or automatic draft loss.
- Client shared requests need a bounded body read and `finally` eviction. Unmounted consumers must ignore late results. Background resume checks absolute elapsed time, not only a delayed timer callback.
- The Vite adapter is intentionally matched against the installed vinext implementation and fails the build on contract drift. It is source-controlled; never patch `dist` or `node_modules` manually.

## Test entry points

`npm test` builds and discovers all `tests/*.test.mjs`, including the new deadline, identity, metadata, attribute, prefetch and navigation tests, followed by the existing three local PGlite suites. `page-read-worker.test.mjs` loads the actual compiled artifact in workerd with network access limited to synthetic fixtures.

The existing production build now runs `check-page-read-regressions.mjs` before bundling: 40 fast real-function/installed-runtime regressions with no live endpoints. Thus the existing Cloudflare build command runs the page-read gate without infrastructure or workflow changes. Compiled-Worker regressions also remain in the normal complete test suite. A failed gate or changed pinned vinext contract stops publication at build time.

Final diff review additionally found and corrected a defect in this task's first retry implementation: a failed same-path navigation to a new query could retry the previous committed query. `retry-target-before.log` demonstrates failure; the same test passes after distinguishing a page-local retry from a failed navigation target, including an explicitly cleared query. This was caught before commit/publication. Protected dependency stalls (roles and profile separately), network disconnect and subsequent retry are exercised against the actual built Worker, not a replacement loader.

`MARKETO_TEST_UNPATCHED=1` makes the installed-prefetch regression execute the unmodified dependency (expected failure). `MARKETO_AUDIT_WORKER_ROOT` selects an independently built baseline checkout for the same integration and benchmark scripts. The original baseline was exported from the exact starting Git commit without checkout/reset or a new branch. Clean-install verification uses a separately copied filtered worktree and `npm ci --ignore-scripts`; dependency lifecycle scripts are deliberately not part of that check.

Pre-existing text assertions expecting unbounded `fetch(...)` and Service Worker v9 were already stale at the starting HEAD. They now require the bounded loader and actual v10 network wrapper. SQL tests also still expected 29 migrations/23 elevated functions although HEAD contains 31 migrations/29 elevated functions. Expectations now include the exact 0001–0031 sequence and current non-client-callable functions; the existing contact audit runs with `protectedPhones:true`, requiring the protected legacy RPC response to contain no phone. Migration SQL and RLS were not modified. No security or error-versus-empty assertion was relaxed.

On this 4 GB Windows host, the full security suite passed all 27 current-schema subtests before the historical second database failed with PostgreSQL XX000 (`could not extend file`, `Invalid argument`). The exact unchanged five historical assertions passed in a fresh process (`sql-replay-isolated.log`). No SQL/security assertion was removed. One overlapping lint run also exhausted native V8 memory; isolated and subsequent normal sequential lint passed. These are host-test failures, not evidence of a website production failure; the precise native filesystem failure mechanism is not established.

An additional final-review regression executes an interrupted page read: the first controller implementation suppressed the pagehide result and could retain a loading indicator on BFCache return. `pagehide-before.log` fails and `pagehide-after.log` passes after retaining a retryable interruption instead.
