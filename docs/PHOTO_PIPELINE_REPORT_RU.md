## Причины прежних отказов

1. Форма отклоняла оригинал больше 12 МиБ **до** нормализации.
2. Клиент сначала декодировал весь оригинал, затем проверял лимит 50 Мп.
   Последующее уменьшение не предотвращало первоначальное выделение памяти.
3. HEIC/HEIF были в одном списке форматов, но отсутствовали в `accept`.
   Старый тест подставлял фиктивный декодер и не доказывал поддержку HEIC.
4. Ошибка одного файла уничтожала результаты всего текущего выбора.
5. Сервер не должен считать клиентскую перекодировку доказательством безопасности.

Два теста `photo-client-contract` воспроизвели отказ исходного кода; те же
тесты проходят после изменения. Журналы: `photo-baseline.log` и
`photo-client-after.log` в `artifacts/performance-20260908/`.

## Подготовленный путь

Выбор → последовательный авторизованный `/api/photos/normalize` → проверка
размера, сигнатуры и MIME → серверный Images decoder → ориентация и уменьшение
без обрезки → JPEG → удаление APP/COM-метаданных → небольшое превью →
последовательный upload API с проверкой владельца → повторная серверная
нормализация недоверенного запроса → R2 → метаданные → защищённое отображение.

Оригиналы не сохраняются в R2/БД, не передаются в браузерный Image/canvas и
не попадают в кеш ответов. Первичная подготовка и окончательная загрузка
разделены; это означает две серверные обработки. Их стоимость и квоты нужно
проверить до выпуска. План Images не покупался и не включался.

JPEG выбран для совместимости с существующим хранением и браузерами. WebP
может дать меньший файл, но потребует другого проверяемого выходного контракта;
AVIF дороже по кодированию. Сравнение субъективного качества на реальных
фотографиях телефона не проводилось.

## Диапазон и доказательства

| Сценарий | Что проверено |
|---|---|
| Максимум фотографий | **7**, включая существующие; 8-я отклоняется. Старые фото не удаляются |
| JPEG / PNG / WebP | Реальное декодирование синтетических валидных файлов через Sharp |
| Оригинал больше 12 МиБ | Валидный JPEG около 13,2 МБ с большими APP-сегментами; это не реальный снимок камеры |
| 12 / 24 / 48 / 50 / 100 Мп | Реальные JPEG-фикстуры, сохранение пропорций и уменьшение |
| 108 / 200 Мп | Не поддержаны выбранным Images-путём; проверен отказ до полного декодирования по данным заголовка |
| HEIC / HEIF | Согласование MIME и контейнера проверено; настоящее HEVC-декодирование **BLOCKED** |
| EXIF 1–8 | Реальные цветные пиксели после поворотов/отражений проверены локальным кодеком |
| GPS / EXIF | Структурированный GPS EXIF и прочие APP/COM удаляются из результата |
| Повреждение / ложный MIME | Отклонение до постоянного хранения |
| Частичный сбой | Сохранение удачных выбранных файлов; rollback новых метаданных/объектов при ошибке API |

Контракт выбранного binding: до **20 000 000 байт**, **100 000 000 пикселей**,
сторона до **12 000 px**. Выход: JPEG, сторона до **2560 px**, до **4 МиБ**,
пропорции сохранены, без увеличения и обрезки; прозрачность на белом фоне.
Качество 82, при необходимости 72/62 в пределах общего срока 90 секунд.
Это ограничения обработки фотографий, не сроки навигации страниц.

[Документированные ограничения Cloudflare](https://developers.cloudflare.com/images/get-started/limits/)
подтверждают границу 100 Мп. Путь загрузки по URL допускает больший сжатый
файл, но не решает 108/200 Мп и требует отдельного временного хранения оригинала.
Другая инфраструктура для этих режимов самостоятельно не подключалась.

Новые превью ограничены 640 px: до примерно 12 МБ RGBA для 7 квадратных
миниатюр вместо примерно 184 МБ для 7 полных картинок 2560 px. Обработка
последовательная. Это расчёт и тест контракта, не замер RAM на iPhone. Уже
сохранённые фотографии используют прежнюю защищённую выдачу; пик памяти всего
редактора и поведение iOS при нехватке памяти не подтверждены.
