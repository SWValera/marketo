# Надёжность проверки и интерфейс модератора

Обновление продолжает engine `jevu-moderation-3`, ruleset и Structured Output `moderation-ai-observation-v1`. Правила, пороги уверенности, флаги публикации и срок объявления не меняются.

- `/admin` получает компактную страницу одним staff RPC `moderation_dashboard`: карточки, последние решения, первая фотография. История и метрики не входят в начальную загрузку.
- `moderation_case` возвращает основную карточку, характеристики и краткое состояние одним staff RPC. История загружается по раскрытию блока через `get_listing_moderation`. Защищённые фотографии сохраняют прежний same-origin/RLS маршрут.
- Фильтры и карточки обновляются внутри текущего dashboard. Только намерение открыть конкретную карточку (hover/focus/touch) предзагружает её основные данные. Кэш компонента ограничен 8 состояниями и 45 секундами; не использует localStorage, service worker или публичный HTTP-кэш. При решении модератора и возврате фокуса очищается. Каждый запрос и каждая мутация заново проверяет роль на сервере.
- Технические коды доступны только в закрытых по умолчанию технических сведениях. Основные этапы, результаты, ошибки и наблюдения переводятся на RU/KK. Неизвестный код получает нейтральное объяснение, а не показывается как исходный код.

## Решения и повторы

Одобрение допускает пустой комментарий; отклонение и возврат требуют выбранной причины и пояснения. Решение подтверждается отдельной формой. UI показывает результат только после ответа RPC. Вызов `moderate_listing_checked` проверяет content revision под блокировкой и сохраняет request UUID и revision в существующей таблице overrides. Уникальный индекс на actor/request нужен для идемпотентности, не для ускорения каталога. Повтор уже выполненного действия не создаёт вторую запись. Старый callback не меняет актуальную версию. Автоматическая история сохраняется; публикация использует прежний lifecycle primitive.

После технического HOLD отправка неизменённого содержания создаёт новую generation, но повтор активной проверки использует уже имеющийся run. Завершённый совместимый результат без технической ошибки переиспользуется. Явный admin rerun сохраняет прежний контролируемый механизм. Миграция сама не ставит старые объявления в очередь.

## Контракт AI

Responses API использует server-side JSON Schema, strict output и локальный validator. JSON/shape/coverage/provenance остаются обязательными. Неполный OCR остаётся причиной HUMAN_REVIEW, но получает отдельный `ocr_incomplete` вместо ложного `invalid_schema`. Это не разрешение пропустить OCR. Некорректный structured response допускает один повтор в существующем двухвызовном durable ledger. Дневной лимит 50 не меняется. Ошибки никогда не публикуют и не отклоняют объявление.

Prompt различает основной физический предмет и содержимое его экрана, без исключений для бренда. Телевизор относится к существующему `other`, изображение внутри экрана — к `background`. Проверки опасного товара, персональных данных и OCR сохраняются. AI не выбирает финальное решение.

Сохраняется только конечный код validation_issue (`json`, `envelope`, `shape`, `coverage`, `provenance`, `ocr_incomplete`) и прежние usage/latency metadata. Ни значения невалидных полей, ни полный ответ, ни сырой OCR не сохраняются. Поэтому точную причину исторической ошибки, у которой остался лишь `invalid_schema`, нельзя достоверно восстановить задним числом.

Контракт сверялся с официальной [документацией Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Реальные проверки запускаются отдельно от CI, только для явно разрешённых примеров. Обычные тесты используют изолированную БД, synthetic session и mocked provider.

## Миграция / выпуск / возврат

`0043_moderation_reliability.sql` добавляет минимальные receipt/revision metadata и обновляет связанные staff/read/retry процедуры. Применённые 0040–0042 не изменяются. Новые RPC закрыты для anon; внутри проверяют активную роль. Никаких новых ролей, правил, публикаций или backfill при применении нет.

Сначала проверить миграцию на изолированной БД, затем применить транзакцией с коротким lock timeout и выпустить Worker. При возврате Worker предыдущие signatures RPC остаются совместимыми; receipt metadata и история не удаляются. Для технической остановки использовать существующие emergency flags, а не менять данные объявлений. Не откатывать исходный published_at и не перезапускать продвижение.
