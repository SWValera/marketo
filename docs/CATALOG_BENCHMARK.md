# Marketo v1.0 — каталог и ориентиры OLX/Avito

Дата инженерной проверки: 2026-09-04.

## Результат

Marketo использует собственный RU/KK-каталог Казахстана: 1 356 категорий,
16 корневых вертикалей и 1 137 конечных категорий. Для подачи объявления и
поиска из единого typed source генерируются 14 310 category-attribute связей и
84 490 локализованных вариантов значений.

Публичная структура OLX и Avito использовалась как функциональный ориентир, а
не как источник для дословного копирования закрытых справочников:

- OLX публикует иерархию категорий и отдельные страницы для телефонов,
  автомобилей, недвижимости, работы и услуг. Partner API OLX описывает
  категорийные атрибуты, варианты значений и зависимости.
- Avito публикует карту разделов и отдельные вертикали для автомобилей,
  недвижимости, вакансий, услуг, телефонов, детских товаров и оборудования
  для бизнеса. Документация Autoload использует категорийные шаблоны полей.

Официальные ориентиры:

- https://www.olx.kz/sitemap/
- https://developer.olx.kz/swagger/v2/partner_api.yaml
- https://www.avito.ru/sitemap/index.xml
- https://developers.avito.ru/api-catalog/autoload/documentation
- https://www.avito.ru/autoload/documentation/templates

## Что закреплено в Marketo

| Вертикаль | Основные параметры продавца и фильтры покупателя |
|---|---|
| Телефоны и планшеты | бренд и зависимая модель с ручным fallback, память, RAM, SIM/eSIM, экран, ОС, поколение сети, NFC, аккумулятор, ремонт, IMEI; у планшетов отдельно тип подключения Wi-Fi/Cellular |
| Автомобили | марка и зависимая модель, поколение, комплектация, год, пробег, кузов, КПП, топливо, привод, объём и мощность двигателя, руль, состояние, владельцы, регистрация, документы, ДТП, ограничения, VIN |
| Недвижимость | тип объекта, площадь, комнаты/этажность, ремонт и удобства, роль продавца, право собственности, документы, обременения, видимость адреса и коммуникации; аренда отделяет наличие коммуникаций от порядка оплаты коммунальных услуг |
| Работа | зарплата и период, занятость, график, опыт, образование, формат, договор, навыки, языки и права/допуски |
| Услуги | тип цены, формат, выезд, опыт, срочность, гарантия, исполнитель, договор, закрывающие документы, лицензии, оплата и зона обслуживания |
| Техника | отдельные профили для стирки/сушки, холодильников и морозильников, плит/панелей, духовок, СВЧ, посудомоек, пылесосов, климата, мелкой кухни, ухода, здоровья и детских устройств |
| Товары и расходники | состояние, материал, размеры, количество и единица продажи; для расходников — нетто, упаковка, производство, срок годности, хранение, минимальный заказ и сертификация |
| Животные | живые животные отделены от клеток, аквариумов, оборудования и кормов; добавлены вид, возраст, пол, документы, здоровье и параметры конкретного товара |
| Аренда и обмен | смешанные конечные категории имеют обязательный переключатель подтипа; зависимые поля показываются только для выбранного подтипа и очищаются при его смене |

Все конечные категории имеют хотя бы одно осмысленное поле продавца и хотя бы
один фильтр покупателя. Валидатор запрещает пустые словари, неверные зависимости,
циклы, межпрофильную смену типа одного ключа, обязательные скрываемые поля и
повторный вопрос о типе, который уже однозначно задан путём категории.

## Совместимость и rollout

Сравнение с выпущенной миграцией 0017:

- смены data type: 0;
- смены depends_on: 0;
- смены parent option: 0;
- удаляемые прежние option values: 0;
- 394 устаревших category-key связей в 129 категориях заменяются более точными
  профилями.

Для общих стабильных идентификаторов также проверены подписи вариантов: 24
локализованные правки в пяти шаблонах являются исправлениями грамматики/KK,
уточнением казахстанской формы организации или контролируемым уточнением смысла;
переназначений stable value на другой смысл нет. Канонический source добавляет
756 обязательных назначений (746 новых и 10 повышенных из optional), но их
production-включение намеренно отложено до отдельного аудита и backfill.

Миграция `0024_catalog_completeness.sql` работает как полный snapshot и
сохраняет UUID по стабильным `(category, key)` и `(attribute, value)`. Перед
деактивацией прежнего поля или значения её preflight проверяет ссылки из
объявлений и атомарно останавливает транзакцию, если обнаруживает используемые
данные.

Новые обязательные поля выпускаются в два этапа. В production-фазе 1 миграция
сохраняет только уже действовавшие обязательные требования, поэтому старые
черновики не становятся невалидными. Чистый seed содержит канонический полный
required-state. Отдельная будущая миграция может повысить новые поля до
обязательных после аудита/обратного заполнения старых draft/rejected объявлений.

Перед production rollout необходимо независимо проверить фактический ledger:

```sql
select *
from supabase_migrations.schema_migrations
order by version;
```

Затем выполнить zero-reference preflight, применить отсутствующие миграции
строго по порядку и после применения запустить Supabase Database Linter /
Security Advisor.
